💡 Panduan Hemat Token untuk Vibecoder

Panduan praktis membangun aplikasi dengan AI Agent — murah, cepat, dan backend tetap aman
Konteks: Project Ai Teacher Assistant (Klassa) · Berdasarkan data konsumsi aktual story 3–5 · Sep 2026

0 · Pahami Dulu: Dari Mana Token Terbuang?

Setiap giliran (turn) percakapan dengan AI agent, seluruh riwayat konteks dikirim ulang ke model. Makin panjang sesi, makin besar konteks yang dikirim ulang. Ada 3 jenis token dengan harga berbeda:

JenisArtinyaHarga relatif
Input freshToken baru yang belum pernah diprosesMahal (acuan 10x)
Cache readBagian konteks yang sama dengan turn sebelumnya, diambil dari cache serverMurah (~1x)
OutputToken yang model generate (jawaban, kode, tool call)Paling mahal per token
✅ Fakta menenangkan
Cache read yang besar itu tanda bagus, bukan pemborosan. Data aktual project: satu sesi build menyerap 78 juta cache read tapi biayanya cuma ~$2,6. Kalau token itu ditagih sebagai input biasa, biayanya bisa 10x lipat.
❌ Musuh sebenarnya: cache miss & sesi panjang
(1) Cache miss — konteks berubah di tengah sesi (edit file besar, campur topik), seluruh konteks dihitung ulang sebagai input mahal. (2) Sesi panjang — makin lama sesi, makin banyak konteks terbawa di setiap turn. Dua hal ini yang dikendalikan panduan ini.
📌 Data pembanding dari project ini
Sesi yang diawali perintah "analisa mendalam dan menyeluruh" konsisten menyerap 20–70 juta token cache read. Sesi yang diawali path file spesifik (review lens) cuma 40–170 ribu. Perbedaan prompt saja: seratus kali lipat.

1 · Aturan Emas: 1 Story = 1 Sesi

Sesi monster (78 juta token) terjadi karena satu sesi mengerjakan banyak hal: cek progress → hardening → build → fix. Setiap giliran, semua konteks itu terbawa.

✅ LAKUKAN
  • 1 story = 1 sesi build. Selesai → commit → tutup sesi.
  • "Cek progress", "jalankan server", "review git" → sesi terpisah yang pendek.
  • Mulai sesi build langsung dengan path story file.
❌ HINDARI
  • Mixing topik dalam satu sesi ("sekalian cek deploy ya Bro").
  • Sesi melewati batas 1 hari / 1 story.
  • Mengobrol santai di sesi build yang sudah panjang — tiap pesan menambah konteks permanen.

4 · Skalakan Review Lens Sesuai Risiko

Pola 3 review lens (blind hunter / edge-case hunter / verification-gap) bagus — tapi jangan seragam untuk semua story:

Jenis perubahanContoh storyReview
Auth, sesi, rate-limit, migrasi DB, akses antar-roleStory 3, 5, 63 lens penuh + walkthrough
Agregasi/query bacaStory 72 lens: edge-case + verification-gap

✅ Hasil
Hemat 40–60% biaya review tanpa mengorbankan keamanan — story yang kritis tetap dapat perlindungan penuh.

5 · Ambil Keputusan SEBELUM Build

  • Keputusan saat blueprint/elicitation = murah (diskusi, minim tool call).
  • Keputusan di tengah build = mahal: agent sudah baca 10 file, asumsi salah → baca ulang → edit ulang → test ulang.
  • Contoh nyata: Open Question ① Story 7 (skor flat vs GradePolicy/KKTP). Putuskan sekarang, tulis di story file — kalau tidak, tambahan ~0,5–1 juta token + risiko rework.

6 · Keamanan Backend: Kunci dengan Invariants, Bukan Prompt Panjang

Jangan minta "pastikan aman ya" (tidak terukur). Yang terbukti bekerja di project ini — daftar invarian pendek di invoke_dev_with:

8 · Khusus Vibecoder: Aman Tanpa Paham Kode

Vibecoder tidak perlu paham kode untuk aman. Yang perlu dipahami: proses dan bukti. Kode itu urusan agent; tugasmu menjaga kontrak dan verifikasi hasil.

8.1 Ganti "baca kode" dengan "tuntut bukti"

Ketika agent bilang "selesai", jawabanmu cuma satu: "Buktikan." Minta dia menjalankan aplikasi dan mendemokan alurnya (browser automation bisa klik-klik dan screenshot untukmu). Kamu menilai perilaku, bukan kode.

8.2 Lembar uji 5 menit (jalankan sendiri tiap akhir story)

  • Login guru bisa
  • Login siswa NIS + PIN bisa
  • PIN salah 5x → terkunci
  • Buat quiz → siswa kerjakan → nilai muncul di dashboard guru
  • Siswa A tidak bisa lihat data Siswa B
  • Ganti PIN → login pakai PIN baru berhasil

5 menit klik menggantikan 90% kebutuhan memahami kode. Kalau ada yang gagal di checklist, baru agent yang bedah teknisnya.

8.3 Git adalah jaring pengamanmu

✅ Cukup 2 kebiasaan
  • Commit sebelum mulai story → titik aman; build berantakan = rollback 1 perintah, nol kerugian.
  • 1 story = 1 commit → kalau rusak, tahu persis penyebabnya.
❌ Akibat kalai diabaikan
  • Tanpa titik aman, satu build buruk bisa menular ke area yang tadinya baik.
  • Commit campur aduk = tidak bisa rollback selektif.

8.4 Kekuatan vibecoder ada di SPEC, bukan kode

  • Tulis perilaku di story file dengan bahasa manusia yang presisi — contoh bagus: "siswa tanpa NIS tidak punya jalur klaim".
  • Istilah tidak paham? Tanya: "jelaskan pakai bahasa sederhana + analogi" — ~500 token, mental model menempel lama.
  • Kode boleh tidak dipahami, syaratnya perilaku terverifikasi (8.1 + 8.2).
