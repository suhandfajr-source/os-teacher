## Findings

### Migration file content has no verification — tests verify the already-mutated Neon DB, not the file that fresh environments and production replay

- **Changed surface:** new migration `prisma/migrations/20260920135945_student_portal_foundation/migration.sql` (e.g. `platformRole` at :22, `audit_log` at :25, `class_joinCode_key` at :46), paired with the additive changes in `prisma/schema.prisma:163,277-283,378-380,923`.
- **Impacted consumer or site:** `prisma migrate deploy` replay on any fresh database — declared as the production path in story 1a's own Verification section (`1a-schema-fondasi-migrasi.md:89` "produksi hanya via `npx prisma migrate deploy`") and used in the documented local recipe (`:60`, 18 migrations replayed via `migrate deploy`). Concretely, every `prisma.user.create`/`update` after `prisma generate` emits the new columns in INSERT/SELECT statements.
- **Existing test evidence:** symbol/reference searches (`rg 'platformRole|accessPinHash|accountStatus|joinCode|AuditLog|auditLog|lockedUntil|pinUpdatedAt|approvedById|failedAttempts|lastLoginAt'` across `src`, `scripts`, `tests`, `prisma/`) return hits **only** in `prisma/schema.prisma` — no test or code references the new surface. The DB-hitting integration tests listed above assert import-session/template/xlsx behavior against the live Neon DB, whose 1a objects were created by `db execute` of a *full* `migrate diff` output, not by this file; the file is a hand-extracted subset of that diff (story Implementation Notes, `1a-schema-fondasi-migrasi.md:57-66`). Also checked: `package.json` (no migrate step in any script; `postinstall`/`build` are schema-driven only), `vitest.config.ts` (includes only `src/**/*.test.ts`, no globalSetup), `vercel.json` (no migration hook), no CI directory. Nothing in any verification path reads or replays the migration file; the only listed check on it is a human-only manual read ("Baca SQL migrasi hasil").
- **Missing verification:** an automated equivalence check that replaying `prisma/migrations` produces the 1a objects in `schema.prisma` (e.g. `npx prisma migrate diff --from-migrations <dir> --to-schema-datamodel prisma/schema.prisma --shadow-database-url <shadow> --exit-code`), or any test touching the file's content.
- **Demonstration:** delete line 22 (`ALTER TABLE "user" ADD COLUMN "platformRole" …`) or line 46 (the `joinCode` unique index) from the migration file. Every verification step the story lists stays green: `npm test` 475/475 (suites hit Neon, which already has the objects from `db execute`), `tsc --noEmit` clean, `prisma validate`/`generate` clean (schema-driven), Vercel build green. The corruption surfaces only at the first fresh replay: every `user` INSERT from the regenerated client errors on the missing column (teacher registration/auth broken on that environment), and `joinCode` uniqueness is silently absent for Story 3/4. The hand-extraction from the applied diff is exactly the step where such an omission would occur, and it is untranscribed by any check.
- **Consequence:** an incomplete or wrong migration file ships undetected while all listed verification passes, and breaks the first environment provisioned via the declared production path (`migrate deploy`).
- **Disposition:** `defer` — the faithful check (`migrate diff --from-migrations → schema-datamodel`) is already red today from the pre-existing schedule/prosem drift queued for reconciliation in `deferred-work.md`, so it can only be enabled as a gate after that out-of-scope reconciliation lands (an `information_schema`/`pg_indexes` integration test in the `import.db-concurrency.test.ts` style would pin the live DB but would not protect the file, so it does not close this gap).

## Other findings

- Story 1a's Verification section lists `npx prisma migrate dev --name student_portal_foundation — applied bersih tanpa warning data-loss` (`1a-schema-fondasi-migrasi.md:89`) as a verification command, but the same story's Implementation Notes (`:59`) record that `migrate dev` demanded a destructive DB RESET due to real drift and was bypassed via `migrate diff` + `db execute` + `migrate resolve`. The listed command is not the path that was actually run and cannot be re-run green on this repo state; anyone re-verifying per the story will hit a reset prompt (destructive if accepted against the connected DB). The reproducible procedure that was actually used exists only in the narrative, not in the commands list.
- `getStudents()` at `src/modules/students/students.actions.ts:94` returns full `Student` rows with no `select` (and `updateStudent`/`archiveStudent` return the full updated row). After this change those payloads include `accessPinHash`, `accountStatus`, `failedAttempts`, `lockedUntil` (all null/default today). Nothing breaks now, but the schema comment constrains only writes ("hanya diisi via hashPin"); the moment Story 1b/3 populate `accessPinHash`, these unprojected server-action returns will ship the PIN hash to the client. Worth projecting columns before Story 3 lands.
